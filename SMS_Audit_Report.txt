11. STUDENT IDENTIFICATION STRATEGY
--------------------------------------------------------------------------------
* Internal Primary Key: users.id (Integer - immutable database primary key).
* Human-Readable School Key: users.id_no (String - Admission / Registration Number).
* Cross-System Identity Resolution:
  Google Classroom User ID (or Google Email)
  ↓ [mapped in SMS users.google_id / google_classroom_student_mappings]
  Laravel SMS Student ID (users.id & users.id_no)
  ↓ [passed via Secure API bearer token & student_id payload]
  CBT Student Identifier (sms_student_id & admission_no)

* Identity Safety: The CBT system must use sms_student_id (users.id) and admission_no (users.id_no) as immutable unique identifiers. Student names will be strictly metadata display fields and never used for entity resolution or lookup.

18. CBT INTEGRATION STRATEGY
--------------------------------------------------------------------------------
Laravel SMS DB
     │
     ▼
Secure Laravel API (/api/v1/cbt/*)  <──[ Sanctum Token Auth ]──>  Pure PHP + React CBT
 (Outputs JSON Resources)                                         (Stores zero SMS passwords)

1. Zero Database Coupling: The Pure PHP + React CBT will communicate exclusively over HTTPS REST API endpoints provided by the Laravel SMS. It will never access the SMS MySQL database directly.
2. Server-to-Server Auth: CBT authenticates using Sanctum tokens with restricted abilities (e.g., cbt:read-rosters, cbt:write-results).
3. Data Payload Standardization: All student, class, and subject records returned to CBT will follow strict API Resource schemas.

--------------------------------------------------------------------------------
19. SECURITY CONSIDERATIONS
--------------------------------------------------------------------------------
* Token Isolation: Google OAuth access/refresh tokens will be encrypted in the SMS database using Illuminate\Support\Facades\Crypt and never exposed to the CBT system or frontend client.
* CBT Data Scoping: CBT will only receive student IDs (users.id, users.id_no), names, class assignments, and exam configurations required to run assessments.
* Rate Limiting & IP Whitelisting: Dedicated API rate limiters (throttle:cbt_api) to prevent denial-of-service or unauthorized enumeration.
* Audit Logging: Every exam result pushed by the CBT system will record the source IP, timestamp, and API client ID.

21. POTENTIAL RISKS
--------------------------------------------------------------------------------
* Email Mismatching: Students having a personal Gmail on Google Classroom that differs from their official email in the SMS. (Mitigation: Roster Matcher UI with manual override).
* API Rate Limits: Exceeding Google Classroom API quota during bulk sync operations. (Mitigation: Dispatch sync tasks using background queued jobs Illuminate\Contracts\Queue\ShouldQueue).
* Token Invalidation: Expiration or revocation of Google OAuth refresh tokens. (Mitigation: Automatic token refresh check in GoogleClassroomAuthService).
